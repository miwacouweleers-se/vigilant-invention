Improving “entity type fields”

Your current design combines a deep hierarchy (categories → fields), per-row configuration (required, order), and custom field creation with enum options. Below are five patterns borrowed from products that handle complex configuration well. Each block is a static mock—meant to spark discussion, not ship as final UI.

1. Stepped wizard 2. Two-pane builder 3. List + detail drawer 4. Reusable value sets 5. Honest category selection

1. Stepped wizard (progressive disclosure)

Inspired by: Stripe (Connect onboarding), Typeform, HubSpot “create object” flows

Split “define the entity type” from “choose and order fields” and “confirm.” Users see one job at a time, which reduces cognitive load when many categories and toggles exist. A review step catches missing required fields before publish.

Step 2 of 3 — Add fields from your library or create custom fields. You’ll set required/optional and order in the next pass or inline per section.

2. Two-pane “on this type” vs “library”

Inspired by: Notion (database properties), Airtable (field list vs table), Figma (assets panel)

The left column is the contract for this entity type only: what appears when someone adds an entity, in order. The right column is the searchable library (by category). Adding is explicit (plus or drag), so users never confuse “browsing the catalog” with “this type uses the field.”

3. Sparse table + configuration drawer

Inspired by: Linear (list → issue detail), Shopify (resource list → edit panel), Gmail (row → side peek)

Keep the main grid readable: name, type, category. Move required/optional, order, and enum editing into a fixed drawer that opens for the selected row. Inactive rows stay clean—addressing the “greyed controls everywhere” problem in dense tables.

4. Reusable enum “value sets”

Inspired by: Salesforce (global picklists), HubSpot (groups + shared dropdowns), Contentful (taxonomy)

When many entity types need the same dropdown, duplicating options in every “Add Field” flow creates drift. Let admins link an existing org-wide value set or fork it. Creation still supports custom one-off enums when needed.

5. Explicit category selection semantics

Inspired by: Gmail (select all in thread), macOS Finder, Asana (multi-select patterns)

A folder-level checkbox should never be ambiguous. Show indeterminate state when only some children are selected, and pair actions with short copy: “Select all 9 fields in Standard” vs “Clear category.” Prevents accidental bulk inclusion.

Combining ideas: A wizard for first-time setup, a two-pane builder for power users, and reusable value sets for enums is a common enterprise pattern (progressive complexity without losing depth).
